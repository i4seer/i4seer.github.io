Tick / How It Works

HOW IT WORKS

From power-on to first reading in ~30 seconds. Per-send transport selection. Self-hosted backend. JSONL on disk.

Boot Sequence

The firmware’s cmdStart() runs seven numbered steps with a per-step retry budget. Steps that fail past their budget cause the bring-up to halt and re-attempt — the device doesn’t pretend network exists when it doesn’t. Sensing is independent of bring-up: even when transport is failing, the device keeps reading the sensor and folding values into the persistent accumulator (see below) so no data is lost while the dispatcher recovers.

[1/7]  host        ESP32-S3 chip info, MAC, firmware version, free heap.
[2/7]  wifi        Associate (skipped if wifi_on=false). Non-fatal.
[3/7]  modem       UART up, AT-OK, ATE0, CMEE=2.
[4/7]  sim         CPIN ready, IMEI, CCID, IMSI.
[5/7]  network     CEREG = HOME or ROAMING. 60s budget.
[6/7]  pdp attach  APN hologram, IP assigned.
[7/7]  state       One state POST to the backend. Non-fatal.

A failed start retries every 10 minutes; the [!] indicator stays in the screen corner until recovery. After 6 consecutive failures, the MCU reboots as a last-ditch reset — the accumulator persists in NVS, so the next boot resumes the same rolling window. No reset of bring-up state ever costs you sensor data.

The Accumulator

Sensing and reporting run on independent cadences. Each sample is folded into a persistent accumulator; reports flush the accumulator on a separate schedule. This makes high-frequency sensing affordable on cellular and survives outages without losing data.

// Accumulator state, persisted to NVS on every read.
// Survives modem reboot, MCU restart, even reboot dtu.

tick             u32   reading sequence number (monotonic)
acc_count        u32   readings in the current window
acc_first_epoch  u32   first reading in the window (UTC seconds)
mcu_lo           i32   minimum value seen this window
mcu_hi           i32   maximum value seen this window
mcu_sum          i64   sum (for avg = sum / count at flush)
mcu_last         i32   most recent value
mcu_last_epoch   u32   timestamp of most recent value

Why Two Cadences

Sample frequency is dictated by the physical event you’re catching (a freezer spike can last 30 seconds). Send frequency is dictated by what your backend, your bandwidth budget, or your cellular plan can absorb (a 30-minute summary is plenty). Decoupling them lets you tune both independently.

Why NVS

If the accumulator only lived in RAM, a power blip or modem reboot would reset the rolling window and the next report would only reflect post-reset readings. Persisting to NVS means the window survives anything short of a flash erase. The acc_first_epoch field tells the backend exactly what time range a report covers.

Why Lo + Hi (not just Avg)

Averages hide outliers. A 30-minute average looks fine even when a 30-second spike crossed your threshold. Reporting lo and hi alongside avg means the alerting layer (or your existing backend) can fire on the actual peak, not the smoothed-out version.

Sensing ↔ Transport Decoupled

The sample loop runs on its own timer, independent of any send. WiFi down, cell down, both down — the device keeps reading and accumulating. When transport recovers, the next send carries the full window, with first/last timestamps so the backend places it correctly on the timeline.

Three Transport Modes

The device has WiFi and cellular pipes built in. Configure which are enabled per device: WiFi only, cellular only, or WiFi with cellular backup. The dispatcher in httpsPostJsonAuto() picks the egress for every send based on what’s enabled and what’s up.

Per-Send Selection (Backup Mode)

In WiFi+cellular-backup mode, the dispatcher tries WiFi first when associated and falls through to cellular on any failure — per send, not per session. A device on a marginal AP fails over immediately rather than waiting for a daemon to notice.

Hysteresis (Backup Mode)

After 3 consecutive WiFi failures the dispatcher skips WiFi for 60s (configurable). A device on a dead AP doesn’t burn an 8s timeout on every send. Window resets on success or expiry. Cell-only and WiFi-only modes don’t apply.

Failure Escalation

3 consecutive total fails → reboot the modem (~25s) and re-associate WiFi. 6 fails → ESP.restart(). Counters are RAM-only — preserving them across reboots would be misleading because the failure context is gone.

Clock Sync Per Pipe

NITZ from the carrier sets the clock on cellular attach. If a device is WiFi-only or boots into WiFi before cell completes, fall back to configTime(0, 0, "pool.ntp.org", ...) over WiFi — carriers block UDP/123 on the cell data path.

HMAC & Identity

Every device-to-server POST is HMAC-SHA256 signed with a secret derived from MAC + per-fleet salt. There is no per-device key registry on the server — the secret is recomputed from MAC at verify-time.


A factory reset, NVS wipe, or reflash all preserve identity because the MAC is hardware-derived. Compromise is recovered by rotating one fleet salt and re-flashing the affected fleet — not by tracking down every device’s key.


Headers ride a single combined X-Tick-Auth: <id>:<ts>:<sig-hex> — the SIM7028’s AT+HTTPPARA="USERDATA" doesn’t interpret literal CRLF, so multi-header attempts collapse into mangled values. One header sidesteps the modem quirk.

Data on Disk

Per-device telemetry is JSONL, one file per UTC day. State snapshots are atomic JSON. A 10-second write buffer with (device_id, tick) dedupe handles cellular retransmits without double-writes.

data/
  orgs.json                          # registry of orgs
  users/{user_id}.json               # per-user identity + memberships
  unclaimed.json                     # HMAC-valid POSTs, no org yet
  audit/{date}.jsonl                 # platform-level audit
  orgs/{org_slug}/
    devices.json                     # per-org device registry
    fleets.json                      # fleets in this org
    device_fleets.json               # device ↔ fleet many-to-many
    audit/{date}.jsonl               # org-level audit
    {device_id}/
      state.json                     # last state snapshot (atomic write)
      {YYYY-MM-DD}.jsonl             # daily readings (10s buffered + dedupe)

In production the data path lives at /var/tick/data/ — outside the repo, so deploys can never clobber it. Backups are rsync; no proprietary export needed.

Multi-Tenant Roles

Org is the security boundary. A device belongs to 0 or 1 orgs. A user belongs to 0 or more orgs, with a per-org role. Fleets group devices for grouping and access — not ownership.

PLATFORM ADMIN

Effective Owner of Every Org

Stored separately from regular users for fail-safe. Creates orgs, assigns initial owners, ejects devices to unclaimed, reads global audit.

ORG OWNER / EDITOR

Full Org Access

Effective fleet editor of every fleet in the org. Owners can manage org members and roles; editors can’t. Both can create fleets and approve devices.

ORG VIEWER

Read-Only Across Org

Sees readings for every fleet in the org. May be elevated to editor on a specific fleet via explicit fleet grants. Cannot manage members.

FLEET MEMBER

Scoped to Granted Fleets

Opts out of the cascade. Sees only fleets where they have an explicit fleet grant. The way to give a contractor access to one fleet without seeing the rest of the org.

The cascade lives in two functions: effective_org_role(user, org) and effective_fleet_role(user, org, fleet). Every access check calls into these — no ad-hoc cascade logic anywhere else.
