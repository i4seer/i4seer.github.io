Tick / Self-Hosted

SELF-HOST OUR BACKEND

Your data, on your server, our code. FastAPI + Caddy + Docker Compose. A $4/mo DigitalOcean droplet handles a meaningful fleet.

One of Three Destinations

Tick supports three deployment modes: bring your own backend, self-host ours, or use the i4Seer-hosted portal. This page covers the second.


Self-hosting is right when you want the Tick dashboard but don’t want telemetry on a vendor cloud — procurement requirement, data-residency rule, or just a strong preference. The backend is one FastAPI process behind Caddy, the data is JSONL files on disk, and the whole thing runs on a small VPS.


If you already have an ingest pipeline, see How It Works for the wire format and HMAC header. If you’d rather not run anything, the i4Seer-hosted portal is the default.

The Stack

FastAPI

Single Python process. Async I/O, atomic file writes, in-memory dedupe buffer. Handles ingest, dashboard render, and admin endpoints from one place.

Caddy

TLS termination + reverse proxy. Auto-renewing Let’s Encrypt. Forced RSA-2048 (the SIM7028’s TLS stack rejects ECDSA). HTTP → HTTPS redirect built in.

Docker Compose

Two services: app + caddy. Host volume mounts ${TICK_DATA_DIR:-/var/tick/data} so deploys can’t clobber your data. docker compose up -d and you’re live.

JSONL on Disk

One JSONL file per device per UTC day. State snapshots are atomic JSON. No database, no migrations, no schema. Backups are rsync /var/tick/data/.

Droplet Sizing

The reference deployment runs on a $4/mo DigitalOcean Basic droplet (1 vCPU, 512 MB RAM, 10 GB SSD). That comfortably handles a small-to-mid fleet at 1-minute reading cadence with 30-min state heartbeats.


JSONL is fine up to a few thousand devices. Beyond that, you’d want indexed time-series storage — TimescaleDB or DuckDB-on-files alongside JSONL — but that’s a future-scale problem, not a deploy-day one.

Deployment, in Order

1.  Reserve a DigitalOcean Reserved IP (so DNS survives droplet swaps).
2.  Add an A record at your registrar pointing your subdomain at the Reserved IP.
3.  ufw allow 80/tcp and 443/tcp. Leave everything else closed.
4.  Drop the backend repo at /opt/tickcell; data path is /var/tick/data.
5.  Generate a per-fleet HMAC salt; write to .env with chmod 600.
6.  docker compose -f docker-compose.prod.yml up -d --build
7.  Watch Caddy obtain the cert (10-30s first time). Verify HTTPS loads with green padlock.
8.  seed-admin a platform admin so the dashboard isn’t locked out of itself.
9.  Flash a device with the matching salt; it auto-provisions to the unclaimed bucket.
10. Approve the device into an org from the admin pages. Live telemetry.

Security Posture

TLS Everywhere

Every device-to-server hop is TLS. Browser-to-portal too. Caddy auto-renews Let’s Encrypt. RSA-2048 forced because the SIM7028 stack rejects ECDSA.

HMAC on Every POST

HMAC-SHA256 with secret derived from MAC + per-fleet salt. No per-device key registry on the server. Single combined X-Tick-Auth header to sidestep modem AT quirks.

Browser Auth

Signed session cookies (not stored server-side). bcrypt password hashes (cost 12). Login is admin-driven today; self-service email reset is on the roadmap.

Org Boundary Everywhere

Every read and write goes through effective_org_role + effective_fleet_role. No ad-hoc cascade in handlers. Two functions, audited on every touch.
